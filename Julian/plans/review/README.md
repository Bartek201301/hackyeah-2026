# Administrator review — research brief

**Researched:** 2026-10-03. **Scope:** Julian's workbench UI research for T07/G3. **Baseline inspected:** local `40ac062`, merged main `8c1484b` ([G0 PR #5](https://github.com/Bartek201301/hackyeah-2026/pull/5)); G1 and review endpoints are not implemented in the inspected tree. The findings below describe accepted behavior and unresolved handoffs, not a working screen.

## User outcome and existing contract

An administrator can inspect a held candidate, understand safe findings/provenance, edit the proposed extract, choose an allowed target classification/audience, give a reason and approve or reject the exact version after a fresh scan. A stale edit must not overwrite another reviewer's work. Candidate content and original inspection are privileged, audited operations; ordinary requesters see a review status/reference only ([PRD](../../../docs/product/requirements.md), [technical spec](../../../docs/product/technical-spec.md), [T07](../../../docs/team/implementation-plan.md)). S06 uses REV-01: only the public webinar sentence may be approved with PUB-02 evidence; the attendee list remains private ([scenario](../../../docs/demo/scenarios.md), [AT05](../../../docs/testing/acceptance.md)).

The [OpenAPI contract](../../../docs/contracts/openapi.json) defines `GET /api/v1/reviews`, `GET /reviews/{id}` and `PUT /reviews/{id}`. `Review` contains ID, version, candidate text, classification, status and document ID. `ReviewRequest` requires `expected_version`, `action` (`approve` or `reject`), candidate text, classification, reason and `evidence_excerpt_ids` (up to five). [Protocols](../../../docs/contracts/protocols.md) specify 409 on stale version, an idempotency key on PUT and a rescan before publication. The [data model](../../../docs/contracts/data-model.md) keeps review versions append-only and candidate text outside browser-readable tables. An admin's role is a server check; hiding the page is only presentation.

## Approach findings

| Question          | Evidence-backed direction                                                                                                                                                                                                                                                                                | Tradeoff to validate after G1                                                                                                                           |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Candidate display | Render candidate text as inert text in a labelled editor; do not interpret PDF/HTML/Markdown from the original. [OWASP prompt-injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) treats retrieved documents as untrusted instructions. | Rich rendering might aid reading but increases exposure and is not required by the design contract.                                                     |
| Exact version     | Keep the visible review version beside the editor and send the server-provided `expected_version`. On 409, preserve the local draft separately, explain that the candidate changed and require a fresh authorized read before resubmission.                                                              | Automatic overwrite/retry is shorter code but would defeat the version check's purpose.                                                                 |
| Evidence          | Choose provenance only from authorized, current, public-approved excerpts when lowering classification, as the [protocol](../../../docs/contracts/protocols.md) requires.                                                                                                                                | `evidence_excerpt_ids` are in the request, but no evidence search/selection route is explicitly tied to review; Bartosz must define the safe UI source. |
| Controls          | Reuse inspected `PageHeader`, `Card`, `Field`, `Textarea`, `Select`, `Button`, `Notice`, `Badge` and `LoadingState`. Native labels and associated errors are supported by [W3C form guidance](https://www.w3.org/WAI/tutorials/forms/validation/).                                                       | Shared `Field` may need an accessible error association; request a shared fix rather than a private duplicate.                                          |

The [technical spec](../../../docs/product/technical-spec.md) says approval records the exact edited version, audience, reason and rescan, with public declassification requiring independent evidence. A UI confirmation cannot override findings. Show the server outcome only after the rescan completes; display `review`, `blocked`, expired or unavailable states without a success banner. If a request loses its response, the idempotency key and fresh GET are safer recovery signals than submitting a new key blindly ([protocol](../../../docs/contracts/protocols.md)).

## States and future evidence

Research states: empty queue; loading/error; candidate pending; edited unsaved draft; missing reason/evidence; rescan in progress; approved; rejected; expired; 409 version conflict; server validation failure; scan or audit outage; role/session change during review. A non-admin should receive server denial without candidate text. Use meaningful status announcements rather than announcing every keystroke ([W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)).

Future evidence maps to S06/AT05 and AT16: approve exact public sentence with PUB-02 evidence, verify version increment and changed text hash, reject stale request, verify rescanning and no original publication, verify non-admin direct API denial, keyboard editing, accessible errors and mobile layout. Bartosz's integration/security tests must inspect stored approved text and audit effects; a UI screenshot alone does not prove publication safety. No review test suite exists at the inspected baseline.
