## User outcome and existing contract

An administrator sees current policy/feed versions, edits valid controls, understands rejected changes and can inspect the next operation's recorded version. The UI must not offer a bypass for required Laya, trusted access checks or central budgets ([requirements](../../../docs/product/requirements.md), [design](../../../DESIGN.md), [T07](../../../docs/team/implementation-plan.md)). S10 demonstrates a new literal feed indicator affecting the next matching request while an unrelated benign request still succeeds; a stale version must fail ([scenarios](../../../docs/demo/scenarios.md), [AT09](../../../docs/testing/acceptance.md)). An expired required feed withholds governed operations ([technical spec](../../../docs/product/technical-spec.md)).

The [OpenAPI contract](../../../docs/contracts/openapi.json) defines `GET/PUT /api/v1/policy` and `GET/POST /api/v1/feeds`. Policy update submits `expected_version` and a complete policy document; feed update submits `expected_version` and a complete feed document. Mutation requests need UUID idempotency keys ([protocol](../../../docs/contracts/protocols.md)). The [policy schema](../../../docs/contracts/policy.schema.json) fixes allowed keys and ceilings; [policy.example.json](../../../docs/contracts/policy.example.json) gives initial values only. The [feed schema](../../../docs/contracts/threat-feed.schema.json) requires schema/version/source/published/expiry and indicators with ID, kind, value, category, action and description. It allows `literal` or `domain` indicators with `REVIEW` or `BLOCK` actions. These shapes do not authorize a browser to choose arbitrary URLs or secret values.

## Approach findings

| Question          | Evidence-backed direction                                                                                                                                                                                                                                                                                                                       | Tradeoff to validate after G1                                                                                                                              |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Policy editing    | A labelled form over the schema's existing fields makes limits, units and errors easier to review than raw JSON. Reuse inspected `Field`, `Input`, `Select`, `Button`, `Card`, `Notice` and `Badge`. [W3C validation guidance](https://www.w3.org/WAI/tutorials/forms/validation/) favors clear field errors while retaining server validation. | Raw JSON is compact for a technical operator but easier to mistype and harder to use on a phone. Do not add a form library solely for this screen.         |
| Feed editing      | A structured indicator list can show the exact `kind`, `category`, `action`, expiry and version from the accepted schema.                                                                                                                                                                                                                       | A JSON paste may suit batch updates, but this demo requires understandable administrator feedback; determine from Bartosz's supported client and schedule. |
| Conflict handling | Display the version being edited, send `expected_version`, and on 409 require a fresh read before a deliberate resubmit. The [technical spec](../../../docs/product/technical-spec.md) calls for immutable snapshots and compare-and-swap head updates.                                                                                         | Automatic resubmission could silently replace another administrator's policy.                                                                              |
| Validation        | Native required/number/date controls improve input, then display the server's safe schema and business-validation errors. [Next.js 16.3.8's installed forms guide](../../../node_modules/next/dist/docs/01-app/02-guides/forms.md) says even server actions must check authorization.                                                           | Browser checks cannot establish rule consistency, feed expiry, or secure access; Bartosz's gateway must decide.                                            |

The [technical spec](../../../docs/product/technical-spec.md) lists business rules beyond JSON Schema: review threshold below block threshold; window overlap below window size; consistent budgets/context; semantic protection required; allowlists cannot introduce new tools/models; no service URLs/secrets; unique feed IDs, valid times and domain syntax. The UI should explain these through server-provided validation feedback, not reimplement an alternative validator. Treat preview/demo environments as writing to the same Supabase project ([architecture](../../../docs/product/architecture.md)); research and browser checks should avoid live policy/feed writes outside coordinated test records.

## States and future evidence

Research states: loading current document/version; no feed or expired feed; editing; field error; submitting; accepted new version; stale-version conflict; invalid schema/business rule; unauthorized; state/audit unavailable; subsequent operation showing previous/new version. Status messages should be announced without constant focus jumps ([W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)). Distinguish a saved configuration from proof that the next request used it.

Future evidence maps to S10/AT09/AT16: stale CAS rejection; invalid shape/regex/source URL/expiry rejection; exact version before and after; next matching request blocked and benign request allowed; admin versus non-admin API access; keyboard editing and 375 px/1440 px layout. These require Bartosz's integration tests and coordinated synthetic data. None have run for this research brief.

## Contract questions and owners

- **Bartosz:** G1's generic client types the policy/feed paths, but live reads/mutations are unavailable. What safe administrator errors will the real endpoints expose? Should forms use the complete document from GET as the edit baseline, or a specific typed projection?
- **Bartosz:** The schema includes policy `version` and feed `version`, while requests also include `expected_version`. Confirm which version fields are read-only in the UI and how conflict feedback names the current head.
- **Bartosz:** What safe field-level validation detail will the API return? OpenAPI's generic error has code/message/retryable only; precise input errors may need a coordinated contract change or a single accessible summary.
- **Bartosz + Nikodem:** Which authorized trace view demonstrates that the next operation used the new policy/feed version? The workbench should link to safe evidence rather than infer enforcement from a success toast.

**Boundary:** Bartosz owns validation, immutable versions, admin authorization, feed publisher token and enforcement. Nikodem owns audit/trace presentation. Julian owns only the administration interaction and safe feedback.
